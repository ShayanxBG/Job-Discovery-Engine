# Changelog

## v2.18.0 - 5 September 2026

First production discovery and ranking runs, and the defects they exposed. Score bands were recalibrated against the ceiling real adverts actually reach, four sources were recovered from being read as dead, and the coverage ledger gained the demotion that stops a source claiming an interval it cannot search. 1,394 vacancies were discovered, read, scored and ranked.

- **Score bands are calibrated against the ceiling real adverts reach, not against 100.** Uncertainty ceilings cap a component backed by incomplete evidence at three quarters of its maximum, so a good real advert reaches technical fit at 40 plus every other component at its partial ceiling: 40+11+18+7+7 = 83. Each threshold is the old one scaled by 83/100 and rounded: 90 to 75, 80 to 66, 70 to 58, 65 to 54. 100 stays reachable IN PRINCIPLE, because a `known` component is uncapped, and the corpus is what makes 83 the right denominator rather than an assumption: of 988 ranked direct adverts NONE had all five components known, none had more than two of the four non-technical components known, company environment was known in 0 and sponsorship in 2, and the highest score observed was 79. Normalising each role by its OWN maximum was tried and rejected because it rewards ignorance: a role with zero known and three unknown components took the highest ratio on the same corpus, outranking one with an exact stack match and a confirmed sponsor.
- **A numeric threshold had four homes and three of them drifted.** `shortlist.py` hardcoded the pre-recalibration bands and rendered a policy Strong Match as `viable`, hiding 53 roles inside the human-review range under a `below` heading. It now derives every floor and heading from the policy, and raises rather than guessing if the policy cannot be read, because the first fix returned no thresholds on failure and silently banded every score as `below`. Instruction PROSE was the fourth home: the deep validator's own invariant table asserted the retired range as a literal, which is a guard that cannot detect the value it guards drifting. It now derives the range from the policy, and the retired wording joined the superseded-rule list so it cannot return to any instruction file.
- **A source that cannot paginate its own results owes no interval.** `family_capability()` gained a third demotion beside cannot-execute-a-query and cannot-verify-freshness: a family whose every enabled source sets `paginate: false` reaches only the first page, so it cannot assert that an interval was searched. It is planned, executed and recorded, and it advances no critical or rolling checkpoint.
- **A declared exploratory bucket could not be recorded at all.** Whether a bucket is MANDATORY is decided on the (inventory family, search family) pair; that answer was then reused to validate the TERM CLUSTER against the required universe only, one granularity too coarse. A family's own exploratory clusters were refused with their declared bucket and refused again without one, making 165 of 223 buckets unrecordable in both directions. The cluster is now checked against every DECLARED bucket. A cluster nobody declares is still refused, so nothing invented reaches the ledger.
- **Four sources were readable and were being recorded as empty.** A browser user-agent alone is not enough for two of them; the complete header set is. One returns a card-less HTTP 200 under throttling, and worse, can return a plausible but wrong result total, so only a retry distinguishes a throttle from a genuinely empty page. Believing such a page truncates the query AND advances its checkpoint over inventory nobody read, so the retry rule is now part of run accounting rather than advice. A transport failure that surfaced as an exit code with an empty body was being reported as a successful empty response; the exit code is now authoritative.
- **A ranking crashed on one character.** A single arrow in one vacancy title killed a whole run on a cp1252 console. Nineteen tools now force UTF-8 on stdout and stderr with replacement, because vacancy text is arbitrary Unicode and the console encoding is not the tool's to assume.
- **The source-confidence table was missing seven of its values,** so several first-party source types ranked BELOW `unknown` when consolidating duplicate sightings, and the weaker sighting won.
- **An explicit sponsorship offer was being captured as evidence and then labelled unknown.** The label was computed during discovery and dropped before the state write, so the single most decision-relevant fact in a sponsorship-aware search was invisible in every shortlist. Negation handling was also too narrow to read an offer phrased as an absence of restriction.
- **Scores now travel with their band name.** The thresholds moved, so a bare number is ambiguous to anyone calibrated on the old scale: 66 reads as mediocre when it means Strong Match. A score reported to a person carries its band, and outside the workspace the band name travels alone.
- **Added the `humanizer` skill,** scoped the way `karpathy-guidelines` is: it governs prose this workspace AUTHORS and never touches evidence, because rewriting a cached advert destroys the quotation a hard blocker depends on. It widens no boundary; sounding human is not authorisation to produce application materials.

## v2.17.6 - 30 August 2026

Phase 4G: the scheduling defect Phase 4F reported and then declared degraded. No candidate fact, matching band, immigration value, CV, dependency, worker definition, global permission, lock behaviour, ATS ceiling, Adzuna decision, initial-catchup budget, exhaustive budget or tier classification changed.

- **Declaring a cadence degraded was the wrong answer to an avoidable defect, and this reverses it.** Phase 4F reported 68 of 73 mandatory buckets covered at a 30-hour cadence, three skipped intervals, five rolling buckets never searched, and classified the critical breach as avoidable. Those are failures to correct, not results to accept.
- **The root cause was per-family allocation.** Each search family planned inside its own budget, so a bucket with an early deadline in one family could not borrow a slot another family was not using. At 30 hours `direct-title` needs eight critical slots per run and has exactly eight in total, which leaves nothing for its five rolling buckets, and no amount of ordering INSIDE a family can fix a shortage that lives BETWEEN families. Deadlines are a property of the workspace, not of a search family.
- **Allocation is now global earliest-deadline-first**, in the documented order: past the 14-day cap, then breached by most overdue, then will-breach-before-the-next-run by earliest deadline, then remaining critical by slack, then remaining rolling by slack, then a route into an inventory family nothing else has reached, then event-driven work holding its own reservation, then exploratory. Term and source diversity survive as tie-breaks, which is what they were always meant to be. Per-family budgets are soft preferences; the global query budget, the event-driven reservation and the ATS ceiling remain hard.
- **Coverage is fixed at every supported cadence.** Thirty consecutive 24-hour runs, thirty consecutive 30-hour runs, thirty alternating 24/30-hour runs, a six-hour delay, a missed run, two failed runs and a seven-day absence all now search 73 of 73 mandatory buckets with ZERO permanently skipped intervals, ZERO never-searched buckets and zero uncovered hours. Both cadences are supported again.
- **Feasibility is now the deadline-safe discrete calculation**, not the average: `max_intervals = floor(target / cadence)` and `required_unique_slots = ceil(count / max_intervals)`. Average capacity is necessary and not sufficient with discrete runs, because a tier needing four slots on average still breaches if the schedule hands it three twice in a row. At 24 hours critical needs 15 unique slots and has 18; at 30 hours it needs 23 and has 23. Both average and deadline-safe results are reported separately, and a fixture at a 50-hour cadence passes the average check and fails the discrete one, which is exactly the difference the model exists to catch.
- **The at-risk horizon is the OBSERVED interval to the next run**, taken from the largest recent gap rather than a fixed 24 hours. At a 30-hour cadence a bucket with 25 hours of slack was comfortable by a 24-hour horizon and breached by the time anything could search it again, so the pull-forward never fired.
- **Revisit targets are improved and not fully met, and that is stated rather than relabelled.** Critical holds its 72-hour target across 30 consecutive daily runs. At 30 hours it reaches 90 and alternating reaches 84; rolling reaches 192 against 168. The deadline-safe arithmetic says both are affordable, so the residue is a scheduling shortfall rather than a capacity one and is recorded as such in policy. Capping rolling at its deadline-safe share to protect critical was tried and measured: it made rolling worse at 216 hours and left critical unchanged at 90, so it was reverted and the measurement kept.
- The bootstrap and exhaustive contracts are preserved exactly: 58 queries funding 45 of 45 critical buckets across 13 of 13 families with 644 raw, 113 deep and 12 ATS; and 100 queries funding 73 of 73 mandatory with zero deferrals, 13 of 13 families and 20 ATS.

- **A rotating family came back and searched the wrong interval, and the workspace had no way to notice.** Phase 4 proved every family eventually returns to the plan. It says a family comes back; it says nothing about what interval the returning query covers.

## v2.17.1 - 30 August 2026

Phase 4B: three ways the workspace could believe it had covered something it had not. No candidate fact, matching weight, band, blocker, uncertainty ceiling, immigration value, permission or dependency changed.

- **The twelve-hour grace was creating exactly the invisible coverage failure that yield-based widening was removed for.** A gap of 30 hours since the last successful run was inside `daily_interval + grace`, so it selected the 24-hour window, and six hours of inventory went unsearched with nothing anywhere reporting it. The reasoning that produced the grace is the usual one: a run started a little late should not be called a missed day. But the cost of the two errors is not symmetric. Re-searching overlap is FREE, because deduplication absorbs it; a shortfall cannot be recovered, because nobody knows it happened. The grace is gone. DAILY and RECOVERY are now two labels on ONE ascending ladder with inclusive upper bounds, and `search_strategy.py` refuses any configuration that reintroduces a grace, starts the ladder above the daily interval, or offers a window shorter than the gaps it claims.
- **Every window decision now proves its coverage rather than asserting it.** `coverage.covers_gap` and `coverage.uncovered_hours` are computed from the window actually selected and returned on every decision, including the ones that cover comfortably, so a shortfall can never be the one case nobody printed. Boundaries: up to and including 24h selects 24h; 24h and one minute selects 7d; up to and including 7d selects 7d; 7d and one minute selects 14d; up to and including 14d selects 14d. `python tools/search_window.py boundaries` probes all ten documented boundaries, and a regression test asserts the probe agrees with the live selector at each one.
- **A gap beyond fourteen days is reported as a shortfall, not described away.** The run says it does NOT achieve full historical coverage, gives the uncovered time in hours and days, and carries deliberate recovery advice. A 30-day gap reports 384 uncovered hours, 16 days.
- **The employer ATS ceiling is an execution boundary now, not a number in a report.** It was declared in configuration, printed in the plan and recorded in the metrics, and nothing stopped a run exceeding it: the breach was visible only afterwards, describing work already done. A limit nobody can enforce is a suggestion. `tools/ats_budget.py` reserves capacity BEFORE each external check and persists the reservation before the caller sees a single employer, so a crash mid-check spends the slot rather than silently freeing it for an unbounded retry. `--limit` can only shorten the list: a caller asking for a hundred tasks in daily mode receives eight. Two requests inside one run cannot return the same employer. A FAILED check still spends its slot, because the ceiling bounds external WORK rather than successes, and refunding failures would let one dead careers page consume a whole run one retry at a time. Reaching the ceiling is `stop_reason: ceiling_reached`, a normal bounded stop, and deferred employers stay enabled and due. Closing a run refuses a ledger that does not reconcile, and metrics distinguish due, reserved, attempted, succeeded, failed, deferred-by-ceiling and abandoned rather than collapsing them into two numbers that cannot tell an exhausted ceiling from an empty watchlist.
- **Every inventory family now declares a monitoring class**, so an omission is a decision with a reason and a review date rather than an accident a coverage percentage absorbs. Exhaustive reaches 13 of 13 enabled queryable families. A daily run reaches the seven `daily` families plus the rotating families due this cycle, nine of thirteen, and its plan lists each omission, its reason, and how many runs until it is due. ## v2.6.2 - 28 August 2026

Phase 3B.1b cache and provenance finalisation. A narrow hardening pass closing Phase 3B.1: no scoring-model change, no new discovery sources, no application surface, and no discovery-state schema migration.

- Fixed a same-run cache-reuse correctness bug. A metadata-only write such as `put --run-id RUN2 --company Acme` recorded `run_id: RUN2`, and a later `get --run-id RUN2` then reported `same_run: true` and reused 75-hour-old evidence that RUN2 had never fetched. Run provenance is now split: `run_id` is metadata naming the run that last touched the entry and never grants reuse, while `description_run_id`, `facts_run_id` and `evidence_run_id` name the run that actually fetched each evidence class. Only those may trigger same-run reuse. Metadata-only and open-status-only writes now grant none, and all four are derived by the cache from what an operation genuinely supplied rather than read from the caller's payload.
- Split description and fact freshness onto independent clocks. One `fetched_at` had covered both, so a facts-only write on an eight-day-old entry made the untouched advert body look freshly fetched. `description_fetched_at` and `facts_fetched_at` now move only when that evidence class is actually supplied, alongside `cached_at` (every write) and `open_status_checked_at` (explicit observation only). `get` reports `description_age_hours`, `facts_age_hours`, `description_fresh`, `facts_fresh`, `reuse_description` and `reuse_facts` independently, `stats` counts stale descriptions and stale facts separately, and `fetched_at` survives only as a derived summary that is never the authority for either class. Pre-split entries stay readable through a clock fallback, and a legacy `run_id` is never promoted to evidence provenance.
- Required a consistent fact-source override. `job_state.py mark --facts-source-url <aggregator>` without `--facts-source-type` had silently completed the pair from the record, storing an employer-ATS `source_type` beside an aggregator URL and host, and the reverse mismatch was possible too. A provenance override is now all or nothing: supply both flags or neither, the host always follows the supplied URL, and a half override is refused with an actionable error. The preferred-source default and the weaker-source fill-only rule are unchanged.
- Cleaned up family-coverage completion semantics. A fully covered run no longer looks incomplete through a legacy boolean: CWJobs `ok` with Totaljobs `changed_layout` is `COMPLETE_WITH_WARNINGS` and now `complete: true`. Completion is reported as three separate facts: `finished` (did the cycle close), `family_coverage_complete` (was every attempted family seen), and `complete`, now aligned with family coverage as finished AND not PARTIAL. An unfinished run is never complete, however healthy its observed families look, and the degraded sibling stays visible as a source warning.
- Updated `/rank`, the scrape rules, `CLAUDE.md` and `README.md` so "cache fresh" is never one undifferentiated fact. The documentation now says that description/facts actually fetched by this run are reusable for that evidence class, instead of implying that any entry a run wrote is reusable.
- Extended the deep validator from 580 to 682 checks using synthetic fixtures. The 102 added checks fail against the Phase 3B.1a implementation and pass after the fix.
